# Plan 001 — Rangos de métricas simuladas

Estado: Aprobado por el usuario

## Alcance y enfoque

Implementar los RF-1 a RF-11 de la spec aprobada sin cambiar el contrato público de `NetworkMonitoringService` ni presentar las fixtures como telemetría real. La interfaz conservará `1h` como selección inicial; las fuentes mock y API devolverán conjuntos deterministas para `1h`, `24h` y `7d`. La validación de respuesta se aplicará en el flujo compartido del hook para que los datos de ambas fuentes cumplan las mismas reglas.

Las ventanas se construirán en UTC desde la muestra más reciente de cada nodo, con extremos incluidos y cadencias exactas: 4 puntos cada 20 minutos para `1h`, 25 cada hora para `24h` y 29 cada 6 horas para `7d`. La página conservará el selector y la etiqueta exacta “Simulated data” en carga, éxito, vacío y error; el estado de nodo inexistente seguirá siendo distinto.

## Enfoque técnico

1. Extender las fixtures mock y las fixtures en memoria de la API para indexar por nodo y rango. Mantener resultados deterministas, cronológicamente ordenados y coherentes entre las nueve combinaciones de nodo/rango. La API mantendrá el valor predeterminado `1h` cuando se omita `range`, responderá 404 para un nodo inexistente y 400 para un rango no admitido.
2. En `NetworkNodeDetailsPage`, mantener el rango seleccionado en estado local, inicializado en `1h` por cada montaje de la ruta. Añadir un control accesible para los tres rangos y colocar “Simulated data” junto a él, fuera de las ramas de estado para que siga visible mientras se cargan o fallan las métricas. El encabezado reflejará el rango actual.
3. En `useNodeMetrics`, validar la identidad del nodo/rango, forma del conjunto, cantidad esperada, marcas de tiempo parseables, orden estricto y unicidad, ventana inclusiva y límites de latencia/pérdida. Un conjunto vacío válido conserva el estado vacío; cualquier conjunto parcial o inválido usa el estado de error existente. Asociar el estado mostrado con el rango solicitado para no presentar durante un render datos de la selección anterior. Mantener cancelación y protección frente a respuestas tardías; el último rango elegido prevalece.
4. Conservar el gráfico y la tabla semántica actuales. Mantener todos los puntos; ajustar la densidad de etiquetas temporales del eje X según el rango si es necesario para que 24 h y 7 días sigan siendo legibles, sin ocultar muestras de la tabla ni añadir visualización de pérdida de paquetes fuera de lo pedido.
5. Sincronizar la documentación vigente con la capacidad terminada, retirando la afirmación de que la API solo admite `1h` y el elemento de roadmap de `24h`/`7d`. Actualizar `MEMORY.md` al completar cada tarea de implementación para mantener el estado real del proyecto. No cambiar la constitución ni añadir dependencias, archivos de código nuevos, cambios de CI, persistencia o telemetría real.

## Alternativas consideradas

- **Calcular muestras al vuelo o mantener fixtures explícitas:** se eligen fixtures deterministas por nodo/rango; facilitan reproducibilidad, inspección y pruebas de la ventana/cadencia, y evitan depender del reloj de ejecución.
- **Validar solo en el servicio HTTP o en cada fuente:** se valida en el hook consumidor común para aplicar las mismas reglas a mocks y API, manteniendo además las pruebas API que aseguran que el backend produce respuestas correctas.
- **Agregar un módulo nuevo de validación o reutilizar el hook:** se mantiene la validación privada en `use-node-metrics.ts` para no crear archivos de código nuevos ni ampliar el límite de servicio. Si la implementación revela una necesidad de reutilización independiente, se detendrá antes de crear otro archivo.
- **Rechazar solicitudes sin `range` o conservar el default actual:** se conserva `1h` para compatibilidad con clientes existentes; los rangos explícitos se prueban de extremo a extremo.

## Riesgos y mitigaciones

- **Errores de conteo o extremos:** las cadencias producen tamaños distintos (4, 25 y 29); verificar en pruebas tanto cantidad como diferencias entre timestamps y ambos extremos.
- **Zona horaria o horario de verano:** generar y comparar instantes UTC, sin cálculos de calendario local; probar límites con timestamps ISO y offsets válidos.
- **Datos obsoletos durante cambios rápidos:** conservar aborto/guardia de actividad y ligar el estado renderizado a la clave de solicitud; probar respuestas fuera de orden.
- **Confusión entre vacío e incompleto:** cero puntos significa ausencia de ancla; cualquier conjunto no vacío que no satisfaga el conteo/forma esperados es error.
- **Discrepancia entre fuentes:** los fixtures mock y API deben cumplir la misma tabla de cantidades/cadencias; ejecutar unitarias, xUnit y full-stack.
- **Etiquetas de gráfico saturadas en ventanas largas:** espaciar ticks según rango sin reducir los puntos ni sacrificar la tabla accesible; comprobar desktop y viewport de 390 × 844.
- **Aceptación de producción no reproducible localmente:** no equiparar CI full-stack con el entorno productivo. El smoke check de producción queda para una validación posterior al despliegue que el usuario autorice.

## Estrategia de verificación

1. Para fixtures y servicios: `npm run test`, con cobertura de los tres rangos, las nueve combinaciones mock, query HTTP y casos de error.
2. Para API: `dotnet test backend/NetworkMonitoring.Api.Tests/NetworkMonitoring.Api.Tests.csproj`; comprobar combinaciones de nodo/rango, cadencias y conteos, rango no admitido (400), nodo desconocido (404) y compatibilidad del rango omitido.
3. Para interacción y responsive con mocks: `npm run test:e2e` en Chromium desktop y móvil de 390 × 844; verificar selección, rango mostrado, etiqueta y navegación existente.
4. Para integración técnica real: `npm run test:e2e:full-stack`, que inicia API local y frontend con `VITE_API_BASE_URL`; validar los tres rangos y 404. Esto no añade el modo API local a los entornos de aceptación de la spec.
5. Para calidad global: `npm run format:check`, `npm run lint`, `npm run build` y `npm run build-storybook`. No se propone editar CI: el workflow ya ejecuta los checks frontend, xUnit, full-stack y Docker.
6. Para RF-11 en producción: tras un despliegue autorizado, comprobar de forma manual que la URL publicada puede consultar los tres rangos y muestra la etiqueta. No se realizará despliegue, promoción ni cambio de variables en esta fase.

## Conflictos documentales conocidos

- `AGENTS.md` afirma actualmente que la API solo admite `1h`, mientras el contrato frontend ya declara los tres rangos; se actualizará esa regla cuando la API quede implementada y verificada.
- `README.md` describe el endpoint como range-aware, pero ejemplifica solo `1h` y conserva `24h`/`7d` como elemento pendiente del roadmap; se sincronizará junto con la capacidad implementada.
- El modo API local está fuera de los entornos de aceptación de la spec, aunque las pruebas full-stack de CI lo requieren como mecanismo técnico. Se mantendrán explícitamente separadas ambas funciones.
