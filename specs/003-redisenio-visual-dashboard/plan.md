# Plan 003 — Rediseño visual integral del dashboard

Estado: Pendiente de aprobación

## Alcance y enfoque

Rediseñar visualmente el inventario y el detalle de nodos como una demo full-stack con datos simulados explícitos. Se conservarán todas las acciones, rutas, datos, estados y relaciones actuales; la composición puede reorganizarse bajo la prioridad de que identidad, estado y mediciones sigan siendo fáciles de localizar y comparar. Se mantiene el tema oscuro, pero la dirección concreta —paleta, tipografía, superficies, composición y movimiento— no se fija en este plan: se seleccionará con Impeccable y requerirá aprobación antes del primer cambio de interfaz.

El trabajo será code-first sobre React y CSS existentes. No se prevén cambios de API, contratos, servicios, dependencias, infraestructura ni funciones. La hoja `src/App.css` concentra los estilos de ambas pantallas y será el punto de escritura compartido; un único implementador será su propietario durante toda la spec. No habrá escrituras de código en paralelo.

## Secuencia técnica y puertas de aprobación

1. Después de aprobar este plan y las tareas, ejecutar `.agents/skills/impeccable/scripts/impeccable concept-seed --scope direction --mode operate` y presentar las direcciones generadas. La persona usuaria elige y aprueba una dirección antes de editar la interfaz. Se respeta `buildPath=code`: no hay ronda de comps y la dirección fija el mundo visual, no la composición final de ambas pantallas.
2. Antes de cualquier cambio de código, asegurar dos referencias code-led independientes: una para el inventario (`/`) y otra para el detalle (`/nodes/:nodeId`). Revisar si el seed de dirección ya entrega una referencia diferenciada para cada superficie; presentar cada referencia por separado y exigir aprobación explícita de ambas. Para toda superficie sin referencia, ejecutar el flujo oficial `.agents/skills/impeccable/scripts/impeccable concept-seed --scope surface --mode operate` en el contexto de esa pantalla, manteniendo fija la dirección aprobada. En Operate/code-first, la referencia seleccionada será el boceto HTML de primer viewport; si el seed no produce boceto, usar únicamente el fallback oficial de wireframe mediante `impeccable serve-question --schema`, también sujeto a aprobación. Si no puede obtenerse y asociarse una referencia aprobable a cualquiera de las dos pantallas, detenerse antes de implementar, explicar que RF-13 sigue bloqueado y pedir autorización para un método alternativo; no sustituirla por la interfaz actual ni inferir aprobación.
3. Resolver la brief sin inventar su ruta: ejecutar `impeccable surface-brief read src/App.tsx`, seguir la ruta/contexto que devuelva y registrar el contrato aprobado con `impeccable surface-brief write <primary-target> <body-file> [related-target ...]`. El contrato tendrá `THESIS`, `OWN-WORLD`, `STORY`, `FIRST VIEWPORT`, `FORM` y `FINISH`; asociará inventario y detalle con sus referencias aprobadas usando solo el formato que soporte la herramienta. Verificarlo mediante otra lectura antes del código. Si no hay un modo soportado para registrar ambas asociaciones, detenerse y pedir autorización en vez de improvisar campos.
4. Implementar únicamente tareas aprobadas, una por vez, con pruebas primero para cambios de comportamiento. Tras las aprobaciones de dirección, referencias y brief, iniciar y avanzar el build gate de Impeccable según sus instrucciones; no trasladar el contrato de dirección al código o contenido servido al navegador.
5. Al acabar el código, ejecutar una sola vez `impeccable detect --json` sobre los targets modificados y atender los hallazgos mecánicos dentro del alcance. Tomar capturas en una ronda batch y revisarlas; corregir hallazgos materiales en un lote y permitir como máximo una ronda de confirmación, conforme al flujo Impeccable.
6. Solo al terminar todo el build, documentar el mundo visual realmente implementado con el documenter oficial de Impeccable y crear/actualizar `DESIGN.md` y `.impeccable/design.json`. No escribir esos artefactos antes de que el diseño esté construido.

## Delegación y control de escrituras

- El coordinador conserva preguntas, aprobaciones, secuencia de build, inspección de diffs y commit final.
- `sdd_implementer` recibe una sola tarea aprobada y evidencia/archivos autorizados. Las tareas de código se ejecutan serialmente. Un único implementador se responsabiliza de `src/App.css` durante toda la spec; otros agentes no la editan.
- Un auditor de diseño realiza análisis de solo lectura antes del build y contrasta después el resultado con la dirección aprobada y los campos esenciales. No decide ni modifica diseño por cuenta propia.
- El rol de Chrome DevTools captura en una ronda batch inventario y detalle en desktop y móvil 390 × 844, además de estados alcanzables con las rutas/mocks existentes. Para el detalle vacío, abrir la nueva story aislada en Storybook y capturarla en desktop y móvil; comprobar que representa un nodo válido con métricas vacías y validar cada imagen visualmente. La story no añade ruta ni modo demo al producto.
- `sdd_reviewer` o el finish reviewer de Impeccable revisa de forma independiente errores de interfaz, accesibilidad, contraste, foco, teclado, movimiento reducido, overflow y consola; no modifica archivos ni aprueba por el usuario. El documenter oficial actúa después del cierre visual.
- Las revisiones read-only pueden ser paralelas. Si la herramienta de subagentes no está disponible durante la ejecución, el coordinador asumirá los roles no delegables en pasadas separadas, dejará constancia de la sustitución y no simulará capturas o revisiones ajenas.

## Alternativas consideradas

- **Rehacer el frontend o migrar de stack:** descartado; el trabajo sustituye el mundo visual sobre las superficies React/CSS existentes y conserva las capas probadas.
- **Adoptar una biblioteca visual o fuente remota:** descartado para este plan; no se añaden dependencias ni solicitudes de red. La dirección escogerá dentro de las restricciones autorizadas; si requiere un asset o dependencia nueva, se pedirá permiso antes.
- **Fijar ahora paleta, tipografía o composición:** descartado; contradiría la selección explícita con `concept-seed` y la aprobación previa exigida por RF-13.
- **Generar comps aunque el proyecto sea code-first:** descartado por el `buildPath=code` registrado y la modalidad Operate. La selección se decide en código con el flujo oficial de dirección; no se inicia una ronda comp-led.
- **Añadir rutas, alertas, monitorización live o controles showcase:** descartado por la spec y la constitución; esta iniciativa solo cambia presentación y movimiento de capacidades existentes.

## Riesgos y mitigaciones

- **Cambios colaterales por CSS global compartido:** reservar `src/App.css` a un solo propietario y hacer escrituras seriales; verificar cada tarea con sus pruebas dirigidas y la matriz responsive completa al final.
- **Pérdida de scanability al buscar una apariencia más expresiva:** usar inventario y métricas reales del proyecto en las revisiones; comprobar explícitamente todos los campos de RF-2 y RF-4 sin hover ni animación.
- **Color semántico insuficiente en dark mode:** contraste WCAG 2.2 AA y estados etiquetados con texto además del color; probar todos los estados, no solo la ruta feliz.
- **Movimiento distrae o afecta sensibilidad:** usar solo respuesta funcional sutil, no reveals decorativos de scroll; probar `prefers-reduced-motion` y preservar contenido/función.
- **Capturas parciales o engañosas por cargas, viewport o DevTools:** esperar estado estable, capturar desde el inicio de página, validar dimensiones y abrir cada PNG antes de presentarlo. Máximo dos rondas visuales batch, sin microciclos ilimitados.
- **Afirmaciones que hagan parecer reales los fixtures:** conservar etiquetas simuladas y ninguna afirmación de uptime/persistencia/telemetría; revisar textos y estados visibles.
- **Falsa cobertura de aceptación de producción:** screenshots y Playwright serán locales; no desplegar ni promocionar. Producción queda fuera de esta spec y requiere petición autorizada aparte.

## Estrategia de verificación

1. Por tarea, ejecutar primero la prueba dirigida pertinente de Vitest o Playwright y después revisar Storybook para las variantes visuales existentes. La accesibilidad de Storybook está configurada como `todo`, por lo que no se tratará como gate automático de CI.
2. Al concluir los cambios frontend: `npm run format:check`, `npm run lint`, `npm run test`, `npm run build`, `npm run build-storybook` y `npm run test:e2e`.
3. Playwright cubrirá inventario y detalle a 375, 390 × 844, 768, 1024 y 1440 px; verificar búsquedas/filtros, selector de rangos, estados aplicables, tablas, teclado, movimiento reducido y ausencia de overflow. No modificar la configuración E2E existente salvo aprobación si resultara imprescindible.
4. Chrome DevTools entregará y verificará capturas desktop/mobile de inventario y detalle, más las variantes de estado alcanzables con las rutas existentes. Para el vacío del detalle, abrir la nueva story aislada y capturarla en desktop y móvil; contrastar su render con el test de página que usa servicio inyectado. Inspeccionar cada archivo y consola.
5. Ejecutar una vez `impeccable detect --json` para los targets realmente modificados; el revisor independiente recibe findings y capturas. No se vuelve a ejecutar el detector ni se afirma que un test visual automatizado existe si no se añadió dentro de archivos autorizados.
6. xUnit y `npm run test:e2e:full-stack` no son parte esperada de esta validación, porque la spec excluye cambios de API/contrato. Se detendrá y se volverá a plan/aprobación si aparece esa necesidad.
7. Después de completar todas las tareas de Spec 003, refrescar Graphify una sola vez mediante su workflow soportado, inspeccionar grafo y reporte, actualizar `MEMORY.md` conforme a AGENTS.md y crear un commit local que incluya solo salidas generadas intencionadas y aprobadas. No hacer push ni deploy sin petición explícita.

## Dependencias y límites

- Requisito previo satisfecho: Spec 003 consta como `Aprobado por el usuario`. Este plan queda pendiente de aprobación; las tareas deberán redactarse y aprobarse en la fase siguiente.
- Antes de cualquier edición visual aún se requieren aprobación del plan, aprobación de `tasks.md`, aprobación del usuario de la dirección Impeccable, referencias code-led independientes aprobadas para inventario y detalle, y lectura de vuelta del contrato en la brief con ambas asociaciones. La story aislada de detalle vacío es el único archivo nuevo autorizado en este plan; cualquier otro archivo nuevo requiere autorización. Si Impeccable no puede proporcionar alguna referencia ni su fallback oficial, pausar antes del código y solicitar autorización para una alternativa.
- Se conservan React, TypeScript, CSS, Recharts, `NetworkMonitoringService`, las rutas, el inglés de interfaz y datos simulados existentes. No se incorpora API nueva, polling, persistencia, autenticación, alertas, dependencia, telemetría real, despliegue ni cambio de CORS.
- Los formatos de aceptación no fijan fuente, valores de color, sistema de superficies ni layout final. Esas decisiones pertenecen a la ronda de dirección aprobada, no a los implementadores.
